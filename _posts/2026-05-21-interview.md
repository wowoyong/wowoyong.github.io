## 오늘의 면접 주제
> Redis 기반 분산 락과 DB 잠금 방식이 함께 자주 쓰이면서, 동시성 제어는 백엔드 면접의 단골 질문이 됐습니다.

## 핵심 한 줄 요약
동시성 제어는 여러 요청이 같은 데이터를 동시에 바꿀 때 데이터 정합성을 지키기 위해, 상황에 맞는 잠금 전략을 선택하는 일입니다.

## 면접 질문 & 모범 답변

### Q1. 동시성 제어가 왜 필요한가요?
**기본 답변**: 여러 사용자가 같은 자원을 동시에 수정하면 의도하지 않은 값이 저장될 수 있습니다. 대표적인 문제가 Lost Update입니다. 예를 들어 재고가 1개일 때 두 요청이 동시에 주문하면 둘 다 성공하는 문제가 생길 수 있습니다.  
**심화 포인트**: 동시성 문제는 트래픽이 많을 때만 생기지 않습니다. 요청 수가 적어도 같은 시점에 겹치면 바로 발생할 수 있습니다.

### Q2. Optimistic Lock은 어떻게 동작하나요?
**기본 답변**: Optimistic Lock은 "충돌이 드물다"는 가정으로 동작합니다. 데이터를 읽을 때 version 값을 함께 가져오고, 수정할 때 version이 그대로일 때만 update 합니다. 중간에 다른 요청이 먼저 수정했다면 update 대상 row 수가 0이 되고, 이때 충돌을 감지합니다.  
**심화 포인트**: 잠그고 기다리게 하지 않는 것이 핵심입니다. 대신 실패한 요청은 재시도 로직이나 사용자 안내가 필요합니다.

```sql
update product
set stock = stock - 1, version = version + 1
where id = 1 and version = 3;
```

### Q3. Pessimistic Lock은 언제 쓰나요?
**기본 답변**: Pessimistic Lock은 "충돌이 자주 난다"는 전제에서 먼저 잠그는 방식입니다. 대표적으로 `select ... for update`를 사용합니다. 다른 트랜잭션은 락이 풀릴 때까지 기다리므로, 같은 데이터를 안전하게 순차 처리할 수 있습니다.  
**심화 포인트**: 안전하지만 대기 시간이 생깁니다. 락 범위가 넓거나 트랜잭션이 길면 성능 저하와 데드락 가능성이 커집니다.

### Q4. Optimistic Lock과 Pessimistic Lock은 어떻게 선택하나요?
**기본 답변**: 읽기가 많고 충돌이 드물면 Optimistic Lock이 유리합니다. 짧은 순간에 같은 row를 자주 수정하면 Pessimistic Lock이 더 단순하고 안전합니다. 즉, 충돌 빈도와 실패 비용으로 선택해야 합니다.  
**심화 포인트**: "성능이 더 좋아서"만으로 고르면 위험합니다. 재시도 비용, 사용자 경험, 트랜잭션 길이까지 같이 봐야 합니다.

### Q5. Redis 기반 분산 락은 왜 필요한가요?
**기본 답변**: DB 락은 보통 같은 DB 안의 row를 보호할 때 강합니다. 하지만 여러 서버 인스턴스가 공통 자원 하나를 두고 경쟁하면, 애플리케이션 레벨에서 조율이 필요할 수 있습니다. 이때 Redis의 `SET key value NX PX 3000` 같은 방식으로 락을 잡습니다.  
**심화 포인트**: Redis 락은 "서버 여러 대 사이의 조율"에는 유용하지만, DB 트랜잭션 자체를 대신하는 도구는 아닙니다.

### Q6. Redis 분산 락의 주의점은 무엇인가요?
**기본 답변**: 락 획득보다 해제가 더 중요합니다. 내가 건 락만 풀어야 하므로 random value를 저장하고, 해제할 때 그 값이 같을 때만 삭제해야 합니다. 그래야 락 만료 뒤 다른 서버가 잡은 락을 실수로 지우지 않습니다.  
**심화 포인트**: 락 만료 시간보다 작업이 길어지면 중간에 락이 풀릴 수 있습니다. 그래서 lease extension이나 작업 시간 예측이 중요합니다.

### Q7. Redis 락만 있으면 데이터 정합성이 완벽히 보장되나요?
**기본 답변**: 아닙니다. Redis 락은 진입 순서를 조절하는 도구에 가깝습니다. 실제 데이터 저장은 결국 DB에서 일어나므로, 중요한 값 검증은 DB 제약조건이나 트랜잭션과 함께 설계해야 합니다.  
**심화 포인트**: 락 하나로 모든 문제가 해결된다고 답하면 위험합니다. 분산 환경에서는 네트워크 지연, TTL 만료, 중복 실행까지 같이 고려해야 합니다.

### Q8. 실무에서 재고 차감은 어떻게 설계하겠습니까?
**기본 답변**: 재고처럼 충돌이 잦은 경우는 DB update 조건으로 1차 방어를 두는 것이 좋습니다. 예를 들어 `stock > 0` 조건으로 원자적으로 차감하고, 실패 시 품절 처리합니다. 필요하면 인기 상품에만 Redis 락을 추가해 순간 경쟁을 줄일 수 있습니다.  
**심화 포인트**: 면접에서는 "한 가지 락 기술"보다 "DB 조건, 트랜잭션, 재시도 정책"을 함께 말해야 실무 감각이 드러납니다.

## 꼬리 질문 대비
- version 컬럼이 없는 테이블에서 Optimistic Lock은 어떻게 구현할 건가요?
- `select for update`가 gap lock이나 next-key lock과 어떻게 연결되나요?
- Redis 장애가 나면 분산 락 전략은 어떻게 바꿀 건가요?
- 재시도는 몇 번까지 할지, 기준은 어떻게 정할 건가요?
- 결제와 재고 차감이 함께 있을 때 트랜잭션 범위는 어디까지 잡을 건가요?

## 헷갈리기 쉬운 포인트
Optimistic Lock은 잠금을 "안 거는" 것이 아닙니다. 충돌을 뒤늦게 감지하는 방식입니다.

Pessimistic Lock은 항상 나쁜 선택이 아닙니다. 충돌이 많고 실패 비용이 크면 오히려 더 단순하고 안전합니다.

Redis 분산 락은 DB 정합성 도구가 아니라 분산 환경의 조율 도구입니다. 핵심 데이터 보호는 결국 DB가 맡아야 합니다.
